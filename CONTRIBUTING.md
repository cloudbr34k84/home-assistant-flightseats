# Contributing to FlightSeats.io

> *Generated by [aurora@aurora-smart-home (ha-integration-dev skill)](https://github.com/tonylofgren/aurora-smart-home)*

Thanks for helping improve FlightSeats. Report reproducible bugs and propose changes through [GitHub issues](https://github.com/cloudbr34k84/ha-flightseats/issues). Include your Home Assistant and integration versions. Remove API keys and personal travel details from reports, logs and diagnostics before sharing them.

## Development setup

Use Linux, macOS or WSL with Git and Python **3.14.2 or newer in the 3.14 series**. The integration supports HA 2026.8+, while the pinned test environment runs HA 2026.11.0.

Fork the repository on GitHub, then clone your fork (replace `YOUR_USERNAME`):

```bash
git clone https://github.com/YOUR_USERNAME/ha-flightseats.git
cd ha-flightseats
git remote add upstream https://github.com/cloudbr34k84/ha-flightseats.git
git switch -c fix/describe-your-change
python3.14 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements_dev.txt
```

No FlightSeats account or API key is needed to run tests. HTTP is mocked; do not introduce live requests in tests or CI. The daily API allowance is shared with the website and all keys belonging to the account.

## Repository layout

```text
custom_components/ha_flightseats/  Integration runtime, metadata, translations and brands
tests/components/ha_flightseats/  Mocked unit and Home Assistant integration tests
.github/workflows/tests.yaml     PR tests, lint and formatting
.github/workflows/validate.yaml  HACS and Hassfest validation
docs/                           API specification and review notes
hacs.json                       HACS metadata
requirements_test.txt           Pinned HA test fixtures
requirements_dev.txt            Test dependencies and Ruff
```

Keep every runtime dependency inside the integration directory or declare external Python dependencies in `manifest.json`. Keep developer utilities, tests and private data outside that directory.

## Local checks

From the repository root with the virtual environment active:

```bash
python -m ruff check custom_components tests
python -m ruff format --check custom_components tests
python -m pytest tests -q
```

To format changed Python files, run `python -m ruff format custom_components tests`. To run focused tests or save a CI-style report:

```bash
python -m pytest tests/components/ha_flightseats/test_api.py -q
python -m pytest tests --junitxml=test-results/pytest.xml --tb=short
```

Add regression coverage for behavior changes and failures. Tests should cover outcomes such as quota limits, cache reuse, validation errors, state values and unload cleanup.

## Testing in Home Assistant

Use a separate development instance. Copy `custom_components/ha_flightseats` into its `custom_components` directory and restart that instance. Add FlightSeats through **Settings → Devices & services → Add integration**. A real Gold-plan API key is required only for an intentional live check; key validation consumes a request.

Never edit `.storage` or copy your production credentials into test fixtures. Repository changes do not automatically deploy to the running installation. See [DEV_SETUP.md](DEV_SETUP.md) for the current local layout.

## Code conventions

- Use HA's shared aiohttp session, async storage and `dt_util.now()` / `dt_util.utcnow()`.
- Keep runtime objects on typed `entry.runtime_data`; pass `config_entry=entry` to coordinators.
- Keep attributes JSON-serializable, convert timestamps to ISO strings and bound result/event lists.
- Use stable entity unique IDs and frozen, keyword-only entity descriptions.
- Validate API data and user input; preserve quota reserves and request spacing.
- Never log credentials or arbitrary API response/error bodies. Redact private travel plans in diagnostics.
- Keep imports at module scope and helpers imported directly from `homeassistant.helpers`.
- Update both `strings.json` and `translations/en.json` when changing UI messages.

## Pull requests

Explain the problem, resulting behavior and checks run. Update documentation and the unreleased changelog when behavior changes. Keep unrelated refactors out of the PR and review the diff for credentials or personal data.

PRs run **Tests**, **HACS** and **Hassfest**. The Tests job checks Ruff and runs the mocked suite on Python 3.14 / HA 2026.11.0; its JUnit report is uploaded when available. Maintainers can configure branch protection to require these checks in GitHub repository settings.

## Release preparation

Use semantic versions (`MAJOR.MINOR.PATCH`). Version `0.1.3` is the release prepared by this change. Ensure the manifest version matches the changelog and the release tag (for example `v0.1.3`). The `Release` workflow runs when a stable `vMAJOR.MINOR.PATCH` tag is pushed. It verifies the manifest and dated changelog match the tag, runs Tests, HACS and Hassfest, then publishes notes from that changelog section. Update the files, commit and push, then create and push the matching tag; do not create a release manually while the workflow is running. Do not raise the HACS minimum HA version without identifying the API requirement and documenting the change. A local version edit does not publish or deploy a release.
